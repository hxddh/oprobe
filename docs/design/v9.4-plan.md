# oprobe 9.4: review of 9.3.5 and the plan for the next release

Reviewed at `baa02df` (v9.3.5), against `v6.md` §1 ("what oprobe is not") and §8. Every item
below was checked in the code or by running the binary; items marked *to confirm* were not
reproduced and are not planned work until they are.

The release stays inside the product: a profiler for OpenDAL operators, one loop (Profile →
Explain → Prove), one remedy per finding. No new command, flag, finding, preset, config key or
output format. Every user-visible addition is a field or a line inside what already exists.

## 1. Where 9.3.5 stands

What works, run by hand on this commit:

- `oprobe run memory:// -d 2s` ends with `[OK] No finding: client processing dominates`, the
  numbers and the next command. A clean run already says it is clean.
- `oprobe run lab://ratelimit` finds `rate_limit` (high confidence, 100 % of the throttled
  requests explained), names one remedy (`layers.concurrent_limit.http` + `layers.retry.jitter`)
  and the `prove` command that sizes it.
- The convergence suite passes on every lab fault; the overhead bench is 0.96 µs/op (budget 2).

What does not:

| # | Problem | Evidence |
|---|---|---|
| P1 | **A wrong number is printed.** `rate_limit` shows "Fitted request rate 172 requests/s" and stores `rate_ceiling_requests_per_s = 171.75` on `lab://ratelimit`, which allows 100/s (A3, open since 9.3.3) | `show last --detail` on this commit |
| P2 | **The lab's in-flight count ends at the response headers.** `ServerInflightGuard` drops when `serve_s3_request` returns the `Response`, before a shaped body streams (`lab/mod.rs:1111-1143`), so `max_inflight_before_503` undercounts large GETs and the in-flight labs throttle less than they say | code (confirmed; was "suspected" in 9.3) |
| P3 | **An operation that started before `save_and_reset` lands in a future interval.** `start_us` saturates to 0 at the new window's start, then `end_us = start_us + latency` adds the whole latency (`recorder.rs:1464-1470`): an operation 10 s old that ends 1 s after the reset is put at 11 s | code (confirmed) |
| P4 | **A trace cannot say whether retries were linked.** Without `Handle::retry_notify()` every attempt is an operation and `resilience.retries` is 0; nothing in the snapshot, the file or the report tells "not wired" from "no retries" | `grep` of `snapshot.rs`, `file.rs`, `report/`, `findings.rs`: no such field |
| P5 | **The live metrics are thin.** The `otel` exporter records two histograms (`http.client.request.duration`, `oprobe.http.client.request.stage.duration`); `connect` merges DNS, TCP, proxy and TLS although `RequestTiming` has each. Retries, connection reuse and body sizes are in the snapshot only | `otel.rs:1-24` |
| P6 | **The trace → run handoff names only a preset.** `run_command` gives URL, endpoint and `--preset` (`model/trace_file.rs:108`); the trace also knows the object sizes, the range length and the requests in flight | code |
| P7 | **`prove` hides the cost side.** Its secondary metrics are p99 or goodput, throttled ratio and error ratio (`app/prove.rs:2141-2230`); requests per operation and wire bytes per logical byte, already in the report (`bytes.request_amplification`, read/write amplification), are not compared | code |
| P8 | **A clean run gives no next step.** The `[OK]` line has no `next:`; a user who wants the ceiling has to know to raise `-c` or set `--rate` | run output |
| P9 | Evidence repeats itself: "Time in retry backoff 91 %" and "Share of the time it costs 91 %" on one finding; "Failures from the rate limit 0" reads as a broken value | run output |

## 3. Observability

The rule from §1 holds: oprobe is not a monitoring system and adds no exporter of its own.
"Rich and complete" means **the profile captures every signal the wire gives**, and the
`otel` exporter that already exists records what it captures with the standard names, so it
joins OpenDAL's own metrics instead of duplicating them.

| # | Change | Where | Surface |
|---|---|---|---|
| O1 | **Retry linking is a stated fact.** `resilience.retry_linking`: `linked` (a `RetryNotify` exists), `unlinked` (none: attempts are operations, `retries` is not counted), or `not_applicable` (oprobe's own runs). `show` prints one line on an unlinked trace: "retries are not linked: pass `handle.retry_notify()` to `RetryLayer::with_notify`" | `oprobe-trace` snapshot, `report/view.rs` | one field (`#[serde(default)]`, minor) and one line |
| O2 | **`connect` splits into its parts** in the stage metric: `dns`, `tcp`, `proxy`, `tls` instead of `connect` (they still add up to the request) | `otel.rs` | attribute values |
| O3 | **The standard HTTP client metrics the transport already measures**: `http.client.request.body.size`, `http.client.response.body.size` (bytes, per request), `http.client.open_connections` (up-down counter, `http.connection.state` = `active`/`idle`) and `http.client.connection.duration`, with the semantic-convention attributes only | `otel.rs` | 4 instruments, `otel` feature only |
| O4 | **Retries as a counter**: `oprobe.http.client.retries` with `oprobe.retry.reason` = `throttled` / `server_error` / `network` / `timeout` / `tail_cut` (the split A1 already computes), and `oprobe.http.client.retry.backoff.duration` | `otel.rs`, fed by `RetryNotify` | 2 instruments |
| O5 | **Docs**: `docs/embedding.md` gets one table: integration level (layer only with `keep_http_transport(true)`; plus the instrumented transport; plus `retry_notify`) × the signals each gives (operations, requests and stages, connections, retries) | docs | none |

The overhead budget (2 µs/op on `memory://`) holds with `otel` off, and the bench gains an
`otel`-on line that is reported, not gated.

## 4. Closing the loop, easier to use

| # | Change | Surface |
|---|---|---|
| L1 | **The trace → run command reproduces the traffic** (P6): `--object-size` from the trace's size distribution (a `dist:` value when it spreads), `-c` from the peak requests in flight, the range length when reads are ranged. Used by `show <trace>` and by `prove <trace>`'s refusal hint | the existing hint text |
| L2 | **`prove` compares the cost side** (P7): `requests_per_op` and `wire_bytes_per_logical_byte` join the secondary metrics (same `SecondaryMetric` shape, so the schema is unchanged), shown on the decision screen and in the app's Compare | two rows |
| L3 | **One trade-off note per remedy that has one**: `FoyerLayer` ("caches whole objects: small range reads fetch the whole object once; a concurrent writer's update is seen after eviction"), tail cut and hedging-like remedies ("each cut sends the request again") — in `analysis/catalog.rs`, printed as `note:` under the remedy | one line, existing catalog |
| L4 | **A clean run names one next step** (P8): `next: oprobe run <same> -c <4×>` (or `--rate` for an open loop) to look for the ceiling | the existing `next:` line |
| L5 | **Evidence says each fact once** (P9): drop the duplicated share, print counts that are zero only when zero is the point | text |
| L6 | **No wrong number** (P1): see §5 A3; until the fit is right, the finding names the rate limit without a figure and `rate_ceiling_requests_per_s` is omitted (it is optional in the schema). `prove` sizes the remedy by measuring, as it does now | text, one optional field left out |

## 5. Correctness

| # | Fix | Test that fails on 9.3.5 |
|---|---|---|
| C1 (P2) | The lab holds its in-flight permit until the response body has been sent (move the guard into the body stream) | a shaped 4 MiB GET at `max_inflight_before_503: 1` makes a second request get 503 while the first body streams |
| C2 (P3) | Compute the completion instant first, then clamp it to the window: `end_us = (started + latency).saturating_duration_since(window_start)` | an operation started 10 s before `snapshot_and_reset` and ended 1 s after lands in the interval of 1 s |
| A3 | **Time-boxed** (two days): fit the token bucket with an unknown initial fill (`f0 ∈ {0, ¼, ½, 1}` as a profiled parameter) and score only requests sent while the replayed bucket is below one token; the base rate is the served rate over the whole throttled stretch. Ship only if `lab://ratelimit` (100/s, burst 30) fits within ±15 % **and** the convergence suite passes; otherwise L6 stays | `lab://ratelimit` fitted rate in [85, 115] |

*To confirm* (each needs a reproduction first): `verify_writes` reporting `corrupted` for a
client-timed-out write the server stored; a `ShieldWriter` dropped during
`CreateMultipartUpload` orphaning the new upload id; `OpGuard` settling as `cancelled` when an
inner timeout cuts one attempt under an outer `RetryLayer`; `Linker` entries outliving their
deadline when traffic stops.

## 6. Not in 9.4

New commands, flags, presets, findings, config keys or output formats; a Prometheus or OTLP
exporter of oprobe's own; a cost model; pre-release dependencies (`rustls` 0.24-dev,
`await-tree` 0.3.2-alpha); OpenDAL layers that are not a remedy; asymmetric-carryover tests in
`prove` (with the few pairs it runs, a test for it has little power and would mostly raise false
alarms).

## 7. Order of work and gate

1. **Dependencies** (§2) first, alone in their own commits, with the full test suite: every
   later change is then tested on the new versions.
2. **C1, C2**, then **O1** (it changes the snapshot), then **O2–O5**.
3. **L1–L5**, then **A3** in its time box, and **L6** if A3 does not land.

Gate, as every release: `OPROBE_BLESS=1` for `cli` and `docs` (the schema diff must be only
O1's field and, if A3 does not land, nothing removed), fmt, clippy with and without `gui` and
the CLI-only variants of `ci.yml`, `cargo test --workspace`, the convergence suite, the overhead
bench, `cargo package -p oprobe-trace`, `cargo deny`.

## Status

Done in 9.4.0, each with a test that fails on 9.3.5: §2 (all upgrades), O1, O2, O4, O5, the
body sizes of O3, L1–L5, C1, C2 and A3. L6 was not needed.

Where the work differed from the plan:

- **O3, connections**: `http.client.open_connections` and `http.client.connection.duration`
  were not added. reqwest owns the connection type its connector returns, so the transport
  sees each dial but never a connection's close; counting open connections would need a
  client of oprobe's own. The body-size metrics shipped.
- **A3** did not need the profiled initial fill: the likelihood still picks the model and the
  burst, and the rate it reports is at most what the service served from the first throttled
  request to the last (an empty bucket serves exactly its refill). `lab://ratelimit` reads
  99.2–99.7/s over three runs.
- **Duplicates**: our crates share `rand` 0.10 and `toml` 1, but the copy counts did not drop
  (`num-bigint-dig` still pulls `rand` 0.8, `rust-i18n-support` `toml` 0.8).
- **`rand` 0.10 changes seeded draws**: the persisted-dataset fingerprint moved to `v3`, and
  one capacity test that held only because of 0.8's draws (no parquet scan's chunks ever
  merged under `read.gap`) now states the real bound.
