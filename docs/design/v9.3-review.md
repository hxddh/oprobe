# oprobe 9.3.3 review: bugs, and what the next release should be

Status: proposal. Date: 2026-11-27. Basis: 9.3.3 (`e24b2e5`), the released binary and source.

This review starts fresh. Four independent passes each covered one part of the product, with the
code and the product's constraints (AGENTS.md, v6 §1 and §8) as their only input:
1. **`oprobe-trace`**: the published layer, meaning the recorder, transports, sampling, files,
   redaction and OTel export.
2. **The engine and its safety**: the runner, workloads, dataset, uploads, gate, guard, cleanup
   and the lab.
3. **Analysis and proof**: findings, limits, statistics, prove, the report and its views.
4. **The user surface**: the CLI, the app adapter, the run store, operator and config resolution,
   errors and the docs.

Each bug below was reproduced. Reproduction used either the release binary
(`target/release/oprobe`, with isolated data directories, the labs, `memory://`, `fs://` and a
local HTTP sniffer) or a temporary test that has since been removed. Items re-checked
independently for this document are marked **re-checked**. Suspicions that were not confirmed
are listed separately and are not planned work.

## Summary

The core is sound:
- the labs name their faults, and sub-ranges of a run match its timeline;
- whole-run percentiles agree across the brief, `--detail` and JSON;
- the proven diff, its Rust and its TOML match what was tested;
- the A/B order is balanced, and the secondary metrics agree with the trials.

The defects cluster in four places:
- **safety at the input edges**: extreme `--rate` values and object sizes, and budgets on local
  schemes;
- **the replay path**, which takes credentials from the wrong operator file;
- **`oprobe-trace` under concurrency and failure**: reset races, failed saves, and exporters that
  see failures late;
- **a few wrong numbers**: throttling is charged with all retry backoff, the edge of a time range
  is miscounted, and a limit's rate is over-fitted.

**The next release fixes these, and the surface gets no bigger.** It adds no command, flag,
preset, config key or file-format field. Several items remove logic or output, and none adds a
concept.

## P0: safety and security

| # | Bug | Reproduction | Root-cause fix |
|---|---|---|---|
| S1 | **Replay sends credentials from an unrelated operator file to the run's endpoint.** A run stores its operator reference as typed, for example a relative `op.toml`. `prove` and the app's Run Again re-resolve it against the *current* directory. They then copy every redacted option from whatever file they find there, without checking that it describes the same operator (`app/profile.rs:157-180`; the same pattern at `app/mod.rs:413`). From a directory with no such file, the secrets are dropped silently and the ambient `AWS_*` credentials are used instead | `oprobe run op.toml` in `proj/` (endpoint E, keys given as values). Then `cd other/` (its `op.toml` names another bucket, with key `OTHERPROJECTKEY`) and run `oprobe prove last --with …`. The sniffer at E received `Credential=OTHERPROJECTKEY/…` | Store operator files by canonical absolute path. Take secrets back only when the resolved operator has the same URL and endpoint as the run; otherwise refuse, with a hint naming the file the run used. **re-checked** (code) |
| S2 | **`--rate` near 1e9 hangs the run past SIGTERM and Ctrl-C, and its test data is never cleaned up.** `ArrivalClock::next` adds `1/rate` to a `Duration`, which truncates to whole nanoseconds, so at 1 ns or less the clock stops advancing (`schedule.rs:367,389`). The missed-arrival loop (`runner.rs:787`) never awaits and never checks cancellation, so it spins | `oprobe run memory:// -d 1s --rate 1e9` is still running 10 s after SIGTERM; only SIGKILL ends it | Bound `--rate` (and `--set rate`) when the input is parsed, to a range the clock can represent. Keep the schedule time in `f64`. The drop loop yields and checks cancellation. **re-checked** |
| S3 | **A tiny `--rate` panics after the dataset is uploaded, and leaves the dataset on the target.** `Duration::from_secs_f64(1.0 / rate)` (`runner.rs:704`) panics, and the unwind skips `Session::close` | `--rate 1e-20` against the lab exits 101; 256 objects and the pending marker remain | The same input bound as S2. Make the session's cleanup run on unwind (a drop guard), so no future panic leaves data behind. **re-checked** (exit 101) |
| S4 | **`--max-requests`, `--max-bytes` and `--max-duration` do not cover dataset upload or preflight on `fs://` and `memory://`.** The guard joins only the measured operator (`runner.rs:410`), and the gate wraps only HTTP transports. The guard's own documentation says dataset preparation goes through it | `run fs://DIR --max-requests 10 --objects 2000` writes 2 005 files, then says "request budget spent: 10 requests". `--max-bytes 1MiB --objects 64 --object-size 1MiB` writes 64 MiB and reports it as "1.0 MiB transferred" | Give the admin and preflight operators of in-process schemes the accounting the HTTP gate gives the others: one small layer that charges the guard and stops when it trips. The reported usage then counts what was actually done. **re-checked** (the run stops with exit 4 only after the upload; cleanup still removes the files) |
| S5 | **A huge `--object-size` aborts the process before any budget applies.** `generate_payload` builds each whole object in memory (`dataset.rs:247`), and the gate admits bytes only as they are sent | `--objects 1 --object-size 64GiB --max-bytes 1GiB` fails with "memory allocation of 68719476736 bytes failed", exit 134. With several multi-GiB objects and `buffered(4)`, an out-of-memory kill mid-upload would leave objects and multipart uploads behind | Before uploading, refuse a dataset whose planned bytes exceed `--max-bytes`. Generate payloads in chunks as they are written |

## P1: wrong numbers and lost data

### `oprobe-trace` (runs in users' production services)

| # | Bug | Reproduction | Root-cause fix |
|---|---|---|---|
| T1 | **A completion that races `snapshot_and_reset` wrecks the next window's timeline.** `window_start` is read before the aggregate lock is taken (`recorder.rs:1361`; also `:1180` and `:1218`). The operation is then bucketed against the old window's start, but into the new window | 4 threads complete operations while one `snapshot_and_reset()` runs. A window only 6 ms old held 502 intervals, from 0 to 3 600 s, and 2 361 of the 2 365 later operations landed in a single interval | Read the window start (and the frozen length) under the same lock as the aggregates, by keeping them in `Agg` |
| T2 | **A failed save loses the data it was saving.** `save_and_reset` resets the aggregates and takes the rows before writing; `save` takes the rows the same way (`lib.rs:465-486`) | `save_and_reset("/nonexistent/p.oprobe")` returns `Err(NotFound)`, and then `snapshot().summary.ops == 0` | Serialise first. Reset and take the rows only after the write succeeds, or restore them on error. **re-checked** (code) |
| T3 | **Concurrent saves to one path corrupt the file.** The temporary file is always `<path>.tmp` (`file.rs:130-142`) | 200 rounds of 2 threads saving to one path give 198 errors and 50 files that do not parse | Use a unique temporary name in the same directory. **re-checked** (code) |
| T4 | **The exporter sees failed requests and failed operations only at the next snapshot.** The last failed attempt of an exhausted retry is parked until a flush (`observe.rs:418-460`), and requests are exported only when their operation completes | A server that answers 503, a `RetryLayer` of 2 and 20 `stat` calls. Before any snapshot the exporter saw 0 requests and 0 failed operations; after one snapshot, 60 and 20 | Export each request when it is captured. Complete a parked call when its task ends or after a short deadline, not only at a flush. An OTel-only user then sees 5xx, 429 and failures as they happen |
| T5 | **A cancelled `OpReader::read` loses its operation for good.** The `active` count is decremented only after the inner read returns (`observe.rs:797-870`). A dropped future leaves it above zero, so the group never completes. `live_ops` and `inflight_ops` then leak, and the leaked live operation holds timeline intervals open | A hanging reader run under `tokio::time::timeout(20ms, …)` and dropped gives `ops 0, inflight_ops 1` | Decrement the count in a drop guard. A group dropped with reads in flight completes as cancelled |
| T6 | **The stale retry-scope map fills up, and then stops linking retries.** A multi-call operation (writer, lister, deleter) whose last temporary failure is not retried leaves its entry behind (`observe.rs:484`). At `MAX_PARKED` entries the map accepts no more | 4 106 failed writers give `scopes held: 4096`. A later writer's retry then counts in `resilience.retries` but not under its verb | Remove the entry when the operation ends, and evict entries by age |
| T7 | **The sampler can exceed `max_rows` about 50 times over.** The slow set is capped in operations, not rows, and `shrink()` evicts only from the reservoir (`sample.rs:188-205`) | One shard (625 rows), fed 20 000 operations of 512 requests each with rising latency, kept 31 806 rows. That is about 509 k rows across 16 shards, against 10 k configured | Cap the slow set by rows, and evict its smallest entries when it is over |

### Analysis and views

| # | Bug | Reproduction | Root-cause fix |
|---|---|---|---|
| A1 | **Throttling is charged with all retry backoff, including the backoff after 5xx.** The finding's cost, severity and headline use the share of all retry time (`findings.rs:669,693,738`) | `run lab://noisy` reports `throttling` as Critical, "87 % of operation time in retry backoff after 429/503", from 7 throttled responses. The `errors` finding beside it (16 × 5xx) claims the same 87 %. Throttling's own share is about 7/23 of that, which would make it a Warning ranked below `errors` | Split the backoff by the status of the attempt each retry followed, and use only the 429/503 part for throttling. **re-checked** (code) |
| A2 | **A range that reaches the end of the window disagrees with the whole run and with the timeline.** The range clamps its upper bound to the window and keeps only requests sent inside it (`report/range.rs:213,223`). Retries of operations in the window are sent after the window ends: the run and the timeline fold them into the last interval, but the range drops them | `run lab://throttle`, then `show RUN --since 0s`: 12 140 requests, 250 retries, 2.81 % throttled. The whole run and its timeline: 12 234, 344, 3.23 %. The app's brushed range shows the same disagreement | When the range reaches the window's end, keep what the timeline folds into its last interval |
| A3 | **The fitted token-bucket rate overstates the limit by about 70 % on the default `lab://ratelimit`.** `served_rate` takes its base from the 250 ms bins that saw throttling (`limits.rs:~307`), and `best_rate` searches only 0.7 to 1.15 times that base (`:398`). With OpenDAL's default retry the workers wake in step, so the throttled bins are exactly the burst bins | The lab allows 100/s. The run reports `rate_ceiling_requests_per_s` = 171.75 and "token bucket of ≈172 requests/s". It served 98/s overall, and a 172/s bucket could not throttle 13 % of that traffic. `prove` uses the figure in its start value and its feasibility guard | Estimate the base over the whole throttled stretch (requests served from the first throttle to the last), not over the throttled bins only |
| A4 | **The "object size" slice puts failed operations into "0 B".** It buckets by bytes moved, which is 0 for a failure (`oprobe-trace/src/dims.rs:206-210`) | `show --detail` on throttle shows "0 B: 1 397 requests, 18.6 % throttled" against "64 KiB–1 MiB: 1.6 %". The 1 397 are HEADs plus 45 failed operations × 4 attempts | Bucket by the object's size (the stat size, or the requested range), not by bytes moved |
| A5 | **The app offers a remedy the core says does not exist.** `ui/data.rs:464-490` falls back to a hard-coded remedy path whenever the core's is empty. For `bandwidth_cap` on reads, the core says "not a layer" and `prove` refuses it, but the app shows `layers.throttle.bandwidth` and a Try button that then fails | `lab://bandwidth` in the app | Remove the fallback and show the core's advice. This deletes logic the app should never have had |

### Engine

| # | Bug | Reproduction | Root-cause fix |
|---|---|---|---|
| E1 | **Constant-rate open loops are capped at about 3–4 k ops/s by oprobe itself, which reports the shortfall as latency and missed arrivals.** The pacer allows a burst of 4 (`runner.rs:704,1079`), and tokio's timer granularity is 1 ms | `memory:// -c 64 -d 2s --rate 20000` (constant arrivals) gives 3 256 ops/s, p50 838 ms and 33 488 missed arrivals. Poisson arrivals at the same rate give 19 981 ops/s and p50 0.9 ms. A closed loop reaches 137 k ops/s | After each wake, dispatch every arrival that is due: a burst of at least `ceil(timer resolution × rate)` |
| E2 | **An open-loop window ends at the last arrival instead of the deadline,** so the achieved rate and throughput are overstated (`runner.rs:839,860`) | `--rate 2 -d 2s --set warmup=0s` gives a 1.50 s window and 2.66 ops/s. `--rate 0.001 -d 1s` reports "1000.0 ops/s" | Close the window at the deadline |
| E3 | **A persisted dataset ignores the size distribution.** The fingerprint omits it (`dataset.rs:91`), so a lognormal-size run reuses a fixed-size dataset | Two runs with `--set persist=true`, first `--object-size 64KiB` then `'dist:lognormal(64KiB,1.5)'`. The second says "reusing persisted dataset", and every object is 65 536 B | Include the distribution in the fingerprint, and bump its version |

## P2: the user surface

| # | Bug | Fix |
|---|---|---|
| U1 | **`--save` on an existing `op.toml` replaces a symlink with a regular file and resets its mode to 0600** (`app/save.rs`, `store::atomic_write`). The file the link points to, the one under version control, is never updated | Write through to the canonical path, keeping the original mode |
| U2 | **`show FILE` and `prove FILE` reject a run or trace file unless its name contains `/` or ends in `.oprobe` or `.json`** (`store/runs.rs`, `looks_like_path`). The docs say files are "recognised by their content, whatever their name" | Treat any path that exists as a file as a file |
| U3 | **A prove refusal repeats the command that caused it.** A run whose window (1 s) is shorter than its warm-up (2 s) is refused with the hint "profile again: `oprobe run … -d 1s`" (`app/prove.rs:2296-2300`) | Hint what changes the outcome: a longer `-d`, or `--set warmup=…`. See also N1 |
| U4 | **Hints name a flag that does not exist**: "use `--http auto` or `--http h1`" (`engine/operator.rs:816-821`). The test that checks hints for real flags scans only `hints.rs` | Name `--set http.version=…`, and make the test scan every hint and error text |
| U5 | **An invalid config file gets the operator-file hint**, capitalised and ending in a period ("The operator file is not valid: Fix the field…"). It comes from a generic rule that matches "unknown field" (`analysis/hints.rs:89`) | Give the config file its own hint, lowercase and imperative, as AGENTS.md requires |
| U6 | **`[defaults] color` is validated but never applied**: `--color` always defaults to `auto` (`store/config.rs:24`, `cli/mod.rs`) | Use the config value when the flag is not given |
| U7 | **A damaged newest run silently disappears from the list, and `last` moves to the run before it** (`RunStore::list`) | List it as damaged |
| U8 | **JSON usage errors drop the missing argument's name**: "the following required arguments were not provided:", with nothing after the colon | Keep clap's whole message |
| U9 | **`ev.typical_transfer_ms` is in neither app catalog**, so the Chinese UI shows the English label. The catalog test does not check dynamic `ev.*` keys | Add the key, and make the test enumerate the evidence keys the core emits |

## The next release

The release is these fixes plus a few simplifications. Each simplification removes a footgun or
some output without adding a concept.

| # | Change | Why | Surface |
|---|---|---|---|
| N1 | **The warm-up adapts to a short run.** The default warm-up (2 s) is longer than `-d 1s`, and such a run cannot be proved; `run` only warns, even under `-q`. When the warm-up is not set, use at most half the window | It removes the most common reason `prove` refuses a run, and U3's hint loop | none: a default becomes proportional; `--set warmup` keeps its meaning |
| N2 | **`--set` and an explicit flag that disagree are refused**, not silently resolved (`-c 4 --set concurrency=8` runs with 8 today) | Two spellings of one setting must not silently disagree | none: an error replaces a silent override |
| N3 | **A multi-operator `run` prints its run ids**, instead of "each run: `oprobe show RUN --detail`" | Today the user must go to `show --list` to find what they just ran | one line per run, replacing one generic line |
| N4 | **`show --list -n` is documented.** It exists but is hidden from `--help` and `cli.md`, while the list and its JSON stop at 20. The docs test also checks hidden flags | A working flag nobody can find | nothing new: an existing flag is documented |
| N5 | **`prove --dry-run` honours `--set max_ops`** (it plans about 125 k operations for `max_ops=10`) | The plan must describe the run it would make | none |
| N6 | **The "no runs yet" hint says `oprobe demo`** instead of pointing at an empty list | It is a dead end on the first command | none |
| N7 | **`show --rm PROVE -o json` lists the trials it removed along with the proof** | The JSON must say what was deleted | none |

**Not in the next release:** new commands, flags, presets, config keys, output formats or file
format versions; new findings or a second remedy per finding; major-version upgrades of
dependencies.

## Suspected, not confirmed (not planned work)

Each is to be confirmed before it is fixed:
- **False "corrupted" integrity results**: a write that the client timed out but the server
  stored (`verify_writes`).
- **The lab never throttles or faults deletes**: `is_delete_cleanup` exempts workload deletes
  too, so delete-heavy mixes look clean on the fault labs.
- **The lab's in-flight count ends at the response headers**, ignoring the body transfer.
- **`lab://timevarying` at the defaults selects an in-flight limit** (medium confidence) over
  the time-varying model, which explains more of the throttling. This is a question of the BIC
  penalty.
- **`hung_requests` on an operator without retry**: its remedy adds `layers.timeout.io` alone,
  while its text says the hung request is retried.
- **Sizing notes when no sizing trial ran**: "no value met --max-throttle", with nothing tested.
- **`oprobe-trace`**:
  - late requests count the cache probe twice;
  - the rows of `Handle::save` can fall outside its snapshot window (the save is not atomic);
  - a reused 4-tuple overwrites a pending dial;
  - `range_len` overflows on a custom `Range` header;
  - a TCP-info lookup runs on a runtime that has shut down.
- **Open-loop latency samples one short of the operation count** when the window closes early
  (related to E2).
- **`fs:///a%20b`** writes to a literal `a%20b` directory. This is a URL-decoding decision
  rather than a confirmed bug.

## Order of work

1. **S1 to S5** first: they can send credentials to the wrong place, leave data behind, or
   break a budget.
2. **T1 to T7**: `oprobe-trace` runs in other people's production.
3. **A1 to A5 and E1 to E3**: wrong numbers.
4. **U1 to U9 and N1 to N7.**

Each fix comes with a test that fails on 9.3.3. For S2, S3, T1, T4, T5, T7 and E1, that test is
the reproduction above. The release is checked as every release is: fmt, clippy (with and
without `gui`), the CLI-only build, `cargo test --workspace`, the convergence suite, the overhead
bench and `cargo package -p oprobe-trace`.
