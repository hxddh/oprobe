# oprobe 9.3 review: what the next release should be

Status: proposal, revised once (see "Revision" at the end). Date: 2026-11-27. Basis: 9.3.3
(`e24b2e5`). Owner decisions taken so far:
- the next release is built on **OpenDAL 0.60**;
- it ships as **one release**, not as a fixes release followed by a migration.

The review had five sources:
- **A hands-on run of the 9.3.3 release binary as a new user would.** It covered every command's
  help, the README and getting-started examples as written, the demo and ten labs (each followed
  to the `next` it printed), `-o json` everywhere, and the error paths. It ran on Linux, without
  cloud credentials.
- **An upstream read** of OpenDAL 0.59.5 (the latest release) and OpenDAL `main` (unreleased),
  hyper 1.13.0, reqwest 0.13.5, foyer 0.22.6, opentelemetry 0.33 and rustls 0.23.
- **A trial port of 9.3.3 onto OpenDAL `main`**: built and tested in a scratch worktree (M1).
- **An independent review of this plan's first draft**, made without the author's reasoning. Its
  corrections are in, and the "Revision" section says what changed.
- **The 9.3.3 release itself**: its CI, its two release runs, and a docs-only PR whose macOS CI
  failed a lab test (T1).

Each item says how sure it is:
- **reproduced**: seen on a binary or in CI;
- **read**: the code path traced, with `file:line`;
- **suspected**: what would confirm it is named.

## Direction

The loop is right, and the stop paths and the statistics are now sound. The remaining gap is
what a user meets first:
- on `lab://noisy` the top finding and its proof point the wrong way;
- a few numbers are unreadable or hide a cost;
- every capacity question still needs a second run;
- the release process has just failed once on its own untested shell.

**The next release is "right the first time, on OpenDAL 0.60".** It adds no command and no flag.
Its file and wire formats stay as they are, except for optional fields that older readers ignore.

1. **Explain is never wrong on a lab** (E): every lab's top finding is the expected one, and
   every printed `next` decides or says why it cannot.
2. **On OpenDAL 0.60, and only on its release** (M): port now against a pinned revision, and ship
   when 0.60 is on crates.io. Take what 0.60 makes possible where it improves an existing remedy:
   `CacheLayer` for `repeated_reads`.
3. **Nothing reads like an internal** (U).
4. **One run answers capacity**, if it passes its acceptance criteria in time (C). It is the
   root fix for E1 and for the queueing finding, and the riskiest change. It ships only if it
   meets every criterion; otherwise it is the first item after this release.
5. **A release and a test suite that cannot surprise** (R, T).

**Not in this release:**
- new commands, flags, presets or output formats (v6 §1);
- OpenTelemetry spans or any export beyond today's metrics (v6 §1: not a monitoring system);
- a second remedy per finding;
- AIMD pacing, hedged reads, and a third rendering of the diff as RFC-9061 config keys (O4, O5:
  evaluated, not shipped);
- renaming the JSON fields that break the unit-suffix rule (U9: they wait for a format bump).

## Versioning: this release is 10.0.0

`oprobe-trace` carries a semver promise (`docs/releasing.md`), and OpenDAL and OpenTelemetry types
are part of its public API:
- `impl opendal_core::raw::Layer for TraceLayer` (`oprobe-trace/src/lib.rs:336`);
- `otel::config(&Meter)` (`otel.rs:72,195`).

Moving them from opendal-core 0.59 to 0.60 and from opentelemetry 0.32 to 0.33, and the MSRV from
1.91 to 1.95, breaks every embedder still on OpenDAL 0.59. Under Cargo's semver that is a major
version. The workspace shares one version, so the product is **10.0.0**.

**The alternative**: give `oprobe-trace` its own version line, as 1.0.0, while the product
becomes 9.4.0. It is not recommended: two numbers to explain, for a library that has never been
published.

What 10.0 does **not** change:
- the CLI and the JSON results stay stable;
- `oprobe.trace/9`, `oprobe.run/7`, `oprobe.report/7`, `oprobe.prove/9`, `oprobe.events/9` and
  `oprobe.operator/6` keep their versions.

That last point holds only if two checks pass:
- **the rows mean the same thing after OpenDAL's RetryLayer rewrite** and the executor move: a test
  compares the trace rows of each lab on 0.59 and on 0.60 (same counts of operations, requests and
  retries within noise);
- **`layers.cache` keeps its fields** under `CacheLayer`: if `CacheLayer` needs more than
  `memory`, its fields are optional with today's defaults.

The first crates.io publish of `oprobe-trace` is this version (R2). `docs/embedding.md` gains a
table of which oprobe-trace goes with which OpenDAL.

## M. On OpenDAL 0.60

**What the trial port found.** 9.3.3 was ported in a scratch worktree, with every `opendal*`
crate patched to OpenDAL `main` at `da2f675`, and run against its test suite:
- **The build.** One change made it compile: the `executors-tokio` feature left `opendal-core`,
  because the Tokio executor is now the crate `opendal-executor-tokio`. Everything else compiles
  unchanged, with deprecation warnings for `FoyerLayer`.
- **The tests.** The suite against `main` first failed nearly everywhere, all with one cause:
  "default executor is not installed". `main` no longer installs an executor implicitly, and
  `opendal::install_default()` (which also installs the executor) must be called where 9.3.3
  calls `init_default_registry()` (`engine/operator.rs:22`).
- **What is left.** With that call the suite runs again; the analysis, capacity and CLI suites
  pass on `main` (the full count follows when the run completes).

**How the dependency is pinned until 0.60 is released:**
- the work happens against a pinned `rev` of OpenDAL `main`;
- a weekly CI job builds against `main`'s head (allowed to fail), so upstream breaks are known
  when they land;
- **the release gate is OpenDAL 0.60 on crates.io**. crates.io refuses a crate with git
  dependencies, and an `oprobe-trace` built against an unreleased OpenDAL would not link with any
  embedder's released one.

OpenDAL has published nothing since 0.59.5 (2026-10-18), although it now has a weekly release
workflow, and there is no 0.60 tracking issue. If 0.60 is not out when everything else is done,
the release waits, as decided. Until then, only fixes that cannot wait go out, as 9.3.x on 0.59.

## C. One run answers capacity, if it earns its place

The known issue of 9.1, 9.2 and 9.3: a steady closed loop cannot tell too few workers from a
saturated service. Users are told to rerun with `--set shape=ramp:…`.

**The idea.** The warm-up, thrown away today, ramps the load in steps (1, 2, 4 … `-c` workers),
and its steps feed the capacity fits as a varied-load sample.

**What it touches**, each a criterion below:
- the warm-up's length, and with it budgets (the guard's operation estimate,
  `guard.rs:509-516`), run time and the demo's;
- `cold_connections`, which counts warm-up dials (`findings.rs:1544-1561`);
- the state in which a lab's limiter enters the window;
- prove trials, which warm up for only 300 ms and prime the tail cut (`prove.rs:63,1584`);
- open-loop `--rate` runs, which have no workers to ramp;
- `halves_agree` (`findings.rs:386-417`), which refits only the window's halves, so a model learned
  from the ramp would stay at medium confidence.

**It ships only if all of these hold, on all three OSes, three passes each:**
1. The window is unchanged. After the ramp, the warm-up holds full load for at least today's
   warm-up time, and the window's numbers on every lab stay within their noise of 9.3.3's.
2. `cold_connections` counts only dials made at full load.
3. The run time grows by at most 2 s at the defaults, and budgets account for the ramp.
4. Prove trials do not ramp: they keep today's warm-up.
5. Open-loop runs do not ramp, and keep the "load was not varied" wording.
6. `lab://queueing` at the defaults yields the queueing finding from one run, and `clean` still
   yields none (`convergence.rs:515`).
7. E1's fix does not depend on it.

If it misses the release, it is the first item after it, and C's deferral wording stays.

Each lab has an **expected answer**:

| Lab | Expected top finding | Expected proof |
|---|---|---|
| demo | `tail_stragglers` | improved |
| throttle | `throttling` | improved, with no secondary loss beyond 10 % unnamed |
| stragglers | `tail_stragglers` | improved |
| bandwidth | `bandwidth_cap` (downlink) | refused: not a layer |
| flaky | `errors` | improved |
| ratelimit | `rate_limit` | improved, with its goodput cost named |
| noisy | `errors` (E1) | improved |
| hotkey | `key_limit` | refused: not a layer |
| parquet | `small_ranges` at its default 6 workers (`throttling` above its limit, with more workers) | improved |
| lossy | `small_ranges` (serial reads split) | improved |
| queueing | none at the defaults (with C: the queueing advice) | not provable |
| timevarying | `rate_limit` (the time-varying model) | improved; it has no convergence case yet, so one is added |
| clean | none: no invented limit | none |

**Done** means all of the following:
- every lab gives its expected answer in three passes on each of Linux, macOS and Windows;
- every printed `next` runs as printed;
- no stderr line contains `{`, `untagged`, `Raw` or an internal type name;
- `demo` plus its proof stays under 60 s on CI's Linux runner (measured by the test, not by
  feel);
- on 0.60, the `oprobe-trace` overhead bench stays at or under 2 µs/op, the real-backend CI
  passes (MinIO, fake-gcs-server, Azurite), `cargo package` passes, and the rows of each lab
  match those on 0.59 within noise.

**Evidence still missing**, to gather during the release:
- one AWS S3 run and one GCS run of a demo-like workload, on 0.59 and on 0.60 (the owner's
  credentials; nothing in this review touched a real cloud);
- a headless app session through `tests/ui.rs` for every changed view;
- the lab table on macOS and Windows.

## What stays as it is

- the command set and the four presets;
- the finding catalog's 13 codes, and their one remedy each;
- the file formats;
- the trace layer's API, apart from its OpenDAL and OpenTelemetry types, which move with them.

## Revision

The first draft of this review proposed 9.4 on OpenDAL 0.59, with the 0.60 work prepared on a
branch for a later release. The owner decided on one release, on 0.60. An independent review of
the draft then found:
- **The version number was not honest.** Moving `oprobe-trace`'s public dependencies is a major
  version, and the release is 10.0.0.
- **E1's fix was a ranking patch over a classification bug,** and it would have buried real
  throttling under `cold_connections`.
- **E3's suspected cause was wrong for its lab.** `lab://throttle` has no token bucket; the
  warm-up and the drain differ.
- **C was under-specified.** "No number in the report moves" was false (`cold_connections`
  counts warm-up dials), and it ignored prove trials, open loops and budgets. It now ships only
  against explicit criteria.
- **The finish line wrongly asked every lab for a fault,** and `clean` must have none. The
  convergence cases the draft wanted to add for noisy, hotkey and queueing already exist.
- **The evidence was lab-only and Linux-only.** What is still missing is named.
- **The draft missed the biggest 0.60 break,** the executor. The trial port confirmed it.

The draft also listed O5 (the diff as RFC-9061 config keys) for 0.60. It is out: it adds an
output and depends on unreleased semantics.
