# oprobe 4.0 — architecture contract

Status: **binding** for all 4.0 work; it amends [v3.md](v3.md) (everything not changed here still
holds). Breaking changes from 3.x are allowed everywhere: run files, reports, flags, JSON fields.
Nothing reads 3.x run files.

**Theme:** *one model, one spec, one loop.* In 3.0, the findings, the simulators, tune, compare,
the App and MCP each computed their own answer. The answers contradicted each other: a suggested
concurrency still throttled, tune "improved" throughput by −61 %, and Verify measured a different
workload. In 4.0, every recommendation comes from one capacity model. Every run is replayable from
its stored spec. Every recommendation is a hypothesis that `verify` confirms or refutes.

Out of scope (unchanged): distributed load generation (4.x), code signing, NSH upstream work.

---

## 1. Run spec — one replayable definition of a run

`src/model/spec.rs`

```rust
pub struct RunSpec {            // Serialize + Deserialize + JsonSchema
    pub profile: Profile,       // the fully resolved profile, secrets redacted ("<redacted>")
    pub target_ref: String,     // as given: target name, URL or lab://scenario
    pub seed: u64,              // dataset/key-choice seed actually used
    pub existing: Option<String>,
    pub label: Option<String>,
}
impl RunSpec {
    pub fn hash(&self) -> String;          // "sha256:<16 hex>" over workload + knobs + target identity (no label/seed)
    pub fn workload_hash(&self) -> String; // workload only (dataset, mix, access, rate, warmup, duration)
    pub fn command(&self) -> String;       // an equivalent `oprobe run …` command line (every non-default)
    pub fn with(&self, o: &Overrides) -> RunSpec;
}
pub struct Overrides { pub knobs: BTreeMap<String, String>, pub workload: BTreeMap<String,String>, … }
```

- The report carries `spec: RunSpec` (Report schema `oprobe.report/4`, run file `oprobe.run/4`).
- **Replay:** `oprobe run --from RUNREF [--set key=value]… [any flag]` rebuilds the run from its
  spec. Flags and `--set` override it, and credentials are resolved again from the target.
- Every rerun or verification command (findings, App, MCP) is `RunSpec::with(overrides).command()`
  or `--from RUN --set …`. Nothing drops warmup, seed, mix, dataset, endpoint, region, HTTP
  version, tail-cut, rate, `--existing` or `--max-ops` any more.
- **One source of defaults:** `config::defaults()` is used by the CLI, the App, MCP and tune. The
  App never hard-codes its own (tune warmup, trials and cooldown, the demo preset).

## 2. Target identity

`src/store/target_id.rs`: `TargetId::of(&TargetSpec) -> TargetId { scheme, authority, root }`

- Lowercase the scheme and host.
- Drop default ports.
- Resolve `.` and `..`; `..` above the root is an error.
- Collapse `//`.
- Strip the trailing `/`, the query and the fragment.
- Map local paths to `fs://` with an absolute path.
- Fold the bucket or container into `authority`.

`TargetId::contains(&self, other) -> bool` is a prefix test on whole path segments.

It is used by:
- `--allow-target`, on both sides normalised (`existing` with `..` is refused);
- baselines;
- compare's "same target" rule;
- cleanup's prefix checks;
- the App's default compare pairing (same target and same `workload_hash`).

## 3. Capacity model — the only source of "how much can I push"

`src/analysis/capacity.rs`

```rust
pub struct Capacity {                           // in the report: `report.capacity`
    pub inflight_ceiling: Option<Ceiling>,      // in-flight requests the server accepts before it throttles
    pub rate_ceiling_requests_per_s: Option<f64>,
    pub per_op: OpShape,                        // request concurrency per op
    pub observed: Observed,                     // peak/mean in-flight, throttled at which level
    pub confidence: Confidence,                 // low | medium | high (+ why)
    pub source: CapacitySource,                 // this_run | tune | history
}
pub struct Ceiling { pub requests: f64, pub lo: f64, pub hi: f64 }
pub struct OpShape {
    pub requests_per_op: f64,                   // mean
    pub peak_inflight_per_op: f64,              // max concurrent requests within one op (maximum over ops)
    pub mean_inflight_per_op: f64,
    pub sequential_fraction: f64,               // share of op time with exactly one request in flight
}
pub fn estimate(reqs: &[ReqRow], ops: &[OpRow], window: Window) -> Capacity;
impl Capacity {
    /// Workers that keep peak in-flight under the ceiling with `headroom_ratio` spare.
    pub fn safe_concurrency(&self, headroom_ratio: f64) -> Option<u32>;
    pub fn predict(&self, concurrency: u32) -> Prediction; // throughput, throttle probability, interval
}
pub const DEFAULT_HEADROOM_RATIO: f64 = 0.15;
```

- **Estimating the ceiling:** reconstruct in-flight requests over time from the request rows
  (start and end times). The ceiling is the in-flight level at which throttled responses start
  (the lowest level with throttling, bracketed by the highest clean level). It is never derived
  from the mean latency × rate.
- `safe_concurrency = floor(ceiling.lo × (1 − headroom) / peak_inflight_per_op)`, at least 1.
- **Users:** every finding that mentions concurrency (throttling, server_latency, small_objects,
  scaling); `simulate::concurrency` (receives the ceiling, never `None` when one is known); tune's
  margin; the App's Verify. No other code computes a safe concurrency.
- Each target's ceiling is saved in `<data>/capacity.toml` (keyed by `TargetId` and
  `workload_hash`), so later runs and tune start from it (`source: history`).

## 4. Correct statistics and definitions

- **Throttling:** `throttled_request_ratio` (throttled responses / requests) and
  `throttled_op_ratio` (ops with ≥ 1 throttled response / ops). The SLA uses
  `throttled_request_ratio`. The bare name `throttle_ratio` is removed everywhere.
- **Throughput counts successful ops only:** `summary.ops_per_s` (good ops) and
  `summary.attempted_ops_per_s`. Compare and tune use the good-op rate.
- **Broken runs:** when `error_ratio` is above the SLA error limit, or the run was interrupted or
  shorter than its warmup, performance findings (latency, scaling, small objects, HTTP, cache, tail)
  are suppressed. A `run_invalid` / `run_partial` finding explains why. `report.run.partial =
  Some(PartialInfo { reason: interrupted|budget|error, measured_s })`; the warning goes into
  `report.warnings`, not only to stderr. A partial run cannot be saved as a baseline.
- **Integer counts:** a `*_count` field is an integer; fractional quantities are `*_mean` /
  `*_ratio`. Ratios are 0–1 in machine output and shown as a % in text, HTML and the App.
- **One percentile estimator:** exact from rows when rows exist (histogram only for streaming or
  live views). Report and compare use the same estimator.
- **Tail-cut:** the simulator uses the real layer's threshold rule (`engine::stack`), shared from
  one function. A run with tail-cut on is never told to "try tail-cut".
- **Errors finding:** advice per error class. A `rate_limited` failure folds into throttling; a
  credentials message appears only for auth classes.
- **Cost:** the storage assumption is explicit: `cost.storage_assumed: bool` and
  `cost.stored_gib`, labelled "(assumed 1 TiB stored — set --stored-gib)" everywhere it is shown.

## 5. Recommendations are hypotheses; `verify` closes the loop

A finding's `verification` becomes:

```rust
pub struct Verification {
    pub overrides: Overrides,           // the change
    pub command: String,                // `oprobe verify RUN CODE` (the CLI way to test it)
    pub rerun: String,                  // `oprobe run --from RUN --set …`
    pub expect: Vec<Expectation>,       // metric, direction, predicted value + interval
}
pub struct Expectation { pub metric: String, pub predicted: f64, pub lo: f64, pub hi: f64, pub unit: String }
```

`oprobe verify RUNREF [CODE|--all] [--repeat N=3]`:
1. Replays the spec with the finding's overrides, interleaving baseline and candidate runs (A B A B…).
2. Compares the two.
3. Answers per finding `confirmed | refuted | inconclusive` against `expect`, with numbers.

Result type `VerifyResult` (schema `verify`). It is also the MCP tool `verify_finding`, and the
App's Verify button (which then opens Compare with the verdict). Outcomes are stored next to the
capacity history and calibrate the predictions: `capacity::calibrate`.

## 6. Tune 4.0

- **Objective:** `goodput` by default (good ops/s or bytes/s, within the throttle budget
  `--max-throttle-ratio`, default 0.001), plus `p99`, `cost` and `balanced`. Throttling within the
  budget is acceptable; the ceiling search respects the budget and does not stop at the first 503.
- **Search:** in-flight, using the capacity model. Bisection near the boundary repeats each trial
  (`--boundary-repeats 2`). The margin is re-checked whenever io_concurrency or range settings
  change in-flight requests per op.
- **Infeasible baseline:** `baseline_feasible: false`. Deltas are reported against the best
  feasible trial and the baseline is shown as "infeasible (X % throttled)". No negative
  "improvement" headline.
- **The cost of the margin** is shown: the best measured value vs the recommended one.
- **Pareto front:** the trials that are not dominated on (goodput, p99, cost, throttling).
- **Result:** `Recommendation { knobs, profile_toml, rust_snippet, vs_baseline, vs_best,
  confirmed: Option<VerifyOutcome> }` (`src/tune/recommend.rs`), in the tune JSON, in MCP
  `start_tune` structured output and in `oprobe fix`. The profile omits environment defaults such
  as `proxy`.

## 7. Compare and the regression gate

- **Identity:** the same `TargetId` and the same `workload_hash` are required for a gate verdict.
  Otherwise the result is `comparable: false` with the differing spec keys, and no regression
  verdict (exit 0 with a warning, or exit 2 under `--strict`).
- **Statistics:**
  - One run per side: a block bootstrap over per-second windows, reported as low confidence.
  - Several runs per side: run-level variance (a t-interval over the run medians).
  - A noise floor per metric, learned from repeated identical runs of the target
    (`<data>/noise.toml`). It is filled by `oprobe baseline calibrate` and by verify's A/A pairs.
  - Count metrics have absolute floors (0 → 1 throttled response is not a regression).
- **Gate checks** are machine-grade: `{ id: "throughput", unit: "ops_per_s", baseline, candidate,
  delta_ratio, limit_ratio, verdict }`; the old prose `name` field is gone.
- **Text compare** sizes its columns to their contents, wraps long values and truncates JSON blobs
  to a readable summary.

## 8. Input, errors, contracts

- `src/input.rs`: one typed parser per input kind (duration, size, rate, URL, preset, access,
  provider (`aws` → `aws-s3`, `gcp` → `gcs`, …), enums, run refs). Each returns
  `OprobeError(Usage…)` with a "did you mean" hint, and the CLI (clap `value_parser`), the config
  loader and MCP all use the same parsers.
- No user input ever yields `internal`. This is enforced by `tests/inputs.rs`, a sweep of bad
  inputs over the CLI and MCP that asserts the code is in `usage.*`, `config.*`, `target.*`,
  `auth.*` or `run.*` and that CLI and MCP give the same code.
- `message_code` substring matching is deleted. Errors are typed where they are raised. Missing
  credentials map to `auth.no_credentials`; a GitHub 403 maps to `network.*`, never `storage.*`.
- **Envelope:** every command's JSON result has `next: Vec<NextStep>` with
  `NextStep { title, cli, mcp: Option<McpCall { tool, arguments }> }` and
  `warnings: Vec<String>`. `next_command`, `next_commands` and MCP's prose `next` are replaced.
- **Formats:** each command declares its supported formats (`CommandOutput::formats()`). clap
  rejects an unsupported `-o` before running, and `capabilities` lists formats per command.
  `completions` and `man` accept only text.
- The unit-suffix and enum-casing schema test walks **every** registered schema, not just the report.

## 9. Agents and MCP

- `--allow-target` uses `TargetId` (§2).
- `lab://` targets are allowed on a read-only server (in-process, nothing external is written).
- **New tools:**
  - `verify_finding` (§5);
  - `recommend_config`, which runs diagnose → tune → verify and returns a `Recommendation` plus
    an applicable profile patch; it is the same as the CLI's `oprobe fix TARGET`;
  - `discover_targets`, which returns credential sources found (AWS profiles and environment, GCP
    ADC, Azure environment), as names only, never secrets; CLI `oprobe target discover`;
  - `sample_objects`, which returns prefixes, counts and size distribution under a target
    (read-only); `doctor` includes a sample.
- Extra tool arguments are rejected (`deny_unknown_fields`).
- `get_run` status flips to `done` atomically with the last event; progress never overshoots its
  total.
- `explain_*` returns `next` with MCP calls.

## 10. Onboarding and distribution

- **Installers** (`install.sh`, `install.ps1`) and `self-update` resolve versions in this order,
  falling back on any failure:
  1. `releases/latest/download/latest.json`;
  2. the `releases/latest` redirect;
  3. the API.

  They add the install directory to PATH: the shell rc file (on a prompt, or with
  `OPROBE_MODIFY_PATH=1`) and the user PATH on Windows, plus the current session. `install.ps1`
  uses `-UseBasicParsing`, a silent progress bar and real ARM64 detection.
- **The demo is the lab:** `oprobe demo` runs exactly `lab://demo` with the `lab://demo` defaults,
  and `lab://demo` resolves to the same bucket, root and preset. The demo's suggested commands are
  `--from` replays, so compare is comparable.
- **Release automation:** a Homebrew tap (`hxddh/homebrew-tap`), a Scoop bucket and a winget PR are
  updated on tag when their tokens exist, and skipped with a warning otherwise. The formula and
  cask get distinct names (`oprobe`, `oprobe-app`).
- **action.yml:** `version: latest-major` resolves the newest `v<major>` release, the comment step
  has `continue-on-error`, the baseline cache is not re-saved, and arguments are quoted.
- **CLI safety defaults:**
  - `doctor` is read-only by default (`--write-probe` opts in);
  - `cleanup` defaults to a dry run (`--yes` deletes);
  - the backend-config error names `--option KEY=VALUE` and `[targets.NAME.options]`;
  - doctor failures show a summarized cause; raw debug output only with `-v`.

## 11. GUI / TUI 4.0

- **Add Target sheet:** URL, region, endpoint and credentials source, with discovery (§9), a
  read-only connection test and save to config. The empty state offers it.
- **Re-run and Verify** use the run's spec (§1) and only edit it. Verify runs `verify` (§5) and
  opens Compare with the verdict banner (confirmed, refuted or inconclusive).
- **Run list:** the list is live (watches the runs directory and refreshes on focus). Partial runs
  have a badge ("partial · budget"); a budget stop is not a failure. "Stopped during warmup" is
  shown instead of 0 ops/s. The list is virtualized with search and "show more", and
  `RUNS (n)` matches what is listed.
- **Compare:** defaults to the same target and `workload_hash`. Selectors shrink with an ellipsis
  and never wrap. Non-comparable pairs show why.
- **Commands:** one context-aware command list drives the menu bar and the ⌘K palette, with the
  same enabled states. It includes Verify, Open run, Switch target, Add target, Fix (recommend)
  and Export.
- **Keyboard:**
  - single-letter shortcuts only when no text field has focus;
  - sheets focus their first field;
  - Enter submits and Esc cancels;
  - a visible focus ring in the TUI.
- **Accessibility:** `kit::btn` always sets an accessible label, and charts expose a text summary
  and a data table.
- **Overview tiles:** a throttling tile (throttled_request_ratio, retry share) next to errors; the
  cost tile labels assumed storage.
- **Layout:** at 120×30 and narrow windows, the run info yields to the tabs, tiles flow onto two
  rows, and Cost becomes one column; numbers never wrap.
- **Live view:** progress per phase (preparing, warmup, measuring, cleanup). Series are appended,
  not rebuilt. The crosshair is drawn on its own layer.
- **Tune view:** the trial table has a header for every column. The result offers "Run with these
  settings", "Verify" and "Save profile".

## 12. Lab convergence test (CI)

`tests/convergence.rs`: against `lab://demo` and a parquet lab scenario, it asserts that:
- the throttling finding's suggested concurrency runs with `throttled_request_ratio` ≤ budget, at
  ≥ 80 % of the best clean goodput;
- tune's recommendation agrees with the capacity model's `safe_concurrency` within ±1;
- no finding on the recommended configuration suggests exceeding the ceiling;
- `verify` confirms the throttling finding.

It runs on Linux CI (release build, about 60 s).

## 14. Streams and file ownership

- **F — foundation** (lead, first; the streams start from it):
  - `model/spec.rs`, `store/target_id.rs`, `input.rs`, the `analysis/capacity.rs` estimator;
  - the `NextStep` envelope; `Verification` / `Expectation` / `Recommendation` types;
  - Report/4 and run/4 wiring, `--from` / `--set`, `config::defaults()`;
  - schemas blessed.
- **A — analysis** (`analysis/{findings,diagnosis,hints,simulate,outliers,stats,cost}.rs`,
  `model/build.rs`, `report/{text,markdown,html}.rs` except compare rendering).
- **T — tune, verify, compare** (`tune/`, `analysis/compare.rs`, compare rendering,
  `cli/verify.rs`, `cli/tune.rs`, `cli/compare.rs`, `cli/fix.rs`).
- **C — CLI and agents** (`cli/` other than T's files, `mcp/`, `errors.rs`, `guard.rs`,
  `engine/operator.rs`, `docs/agents.md`, `skills/`).
- **D — distribution and onboarding** (`scripts/`, `action.yml`, `.github/workflows/release.yml`,
  `packaging/`, `cli/self_update.rs`, `cli/demo.rs`, `lab.rs`, `docs/install.md`, README, CHANGELOG).
- **U — GUI/TUI** (`src/ui/`).

Shared files (`cli/args.rs`, `mcp/schemas.rs`, `schemas/`): additive edits only; the lead
resolves conflicts at integration.
