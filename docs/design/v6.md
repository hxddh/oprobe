# oprobe 6: direction

**Status: proposal.** This follows a deep review of 5.0.0. The evidence is in [v6-review.md](v6-review.md),
with IDs P (product), U (walkthrough), R (architecture), T (trust) and M (market).

**Owner direction (2026-11-22):**
- Don't make the product more complicated.
- Make full use of what OpenDAL already does.
- Build something small, well made and fun to use.
- Deep cuts and a rewrite are acceptable.

## 1. Where 5.0 stands

5.0 works, but it is the wrong shape:

- **Too big.** 104k lines of Rust in three crates. 29 top-level commands, 77 `run` flags, 21 MCP tools
  (54 KB of tool schema per agent session) and 67 JSON Schemas. A native GUI on three operating systems,
  a TUI workbench, distributed workers, four SDK clients, `watch`, `matrix`, `compat`, a hand-written
  OTLP encoder and a self-updater.
- **Built in a vacuum.** The repository is 3 days old, with five major versions in that time. It has
  0 stars, 0 issues from users and 1 unique visitor. Neither CI nor the test suite has ever run against a real cloud bucket; real-backend CI uses MinIO,
  fake-gcs and Azurite.
  The models were designed against oprobe's own lab and validated against that same lab (P1–P3).
- **Weak on its central promise.** "Tell me what to change, then prove it" does not hold up in the
  demo itself:
  - `verify` reports *confirmed* for advice that cost 15.6 % throughput and did not improve p99.
  - `fix` recommends `concurrency=23`, prints `24` as the best option, and its own table shows
    c=24 at 0 % throttling (U1–U3).
  - Advice from an `exec:` client run tells the user to enable an OpenDAL layer that this client does
    not use (U5).
- **Uneven trust.**
  - Throttling diagnoses from a single process are now right: in-flight, token-bucket, per-prefix and
    random 503s, a bandwidth cap, and client CPU.
  - Limits that do not throttle are not handled. On queueing or a plateau, oprobe says "raise
    concurrency" with confidence, and identical runs flip between opposite advice.
  - `run` advice sizes remedies with a fixed 15 % margin. The distributed and `exec:` paths lose
    precision while still reporting "high" confidence (T1–T8).
- **Barely using OpenDAL.** oprobe uses three of OpenDAL's ~25 layers (Retry, Timeout, TailCut). It
  reimplements a cache layer and an HTTP pool, and builds clients that bypass OpenDAL entirely
  (`aws-sdk`, boto3, CRT, Go adapters). The product's distinctive base, OpenDAL, is in the background.

The parts that are good and distinctive:
- per-request stage tracing from the client side;
- a single `.oprobe` file that replays exactly;
- the in-process fault lab, which makes the analysis testable;
- interleaved A/B verification;
- the agent-safe CLI and MCP contract;
- `ClientStack` (`engine/stack.rs`): *the layer stack as data*, one value that both builds the
  measured operator and generates the code to use.

That last one is the seed of 6.0.

## 2. The idea: an operator is a service plus layers, and oprobe finds and proves the layers

In OpenDAL, an application's storage client is an **`Operator` = service + layer stack + read/write
options**. Every performance fix an application can make is a change to that stack:

| Symptom (finding) | The OpenDAL change | Layer / option |
|---|---|---|
| throttling (429/503) | cap requests in flight, back off with jitter | `ConcurrentLimitLayer`, `RetryLayer` |
| bandwidth cap or noisy neighbour | pace the client | `ThrottleLayer` |
| server stragglers (p99 ≫ p50) | cut and re-issue slow requests | `TailCutLayer` |
| hung requests | bound each I/O | `TimeoutLayer` |
| many small range reads | coalesce and parallelise ranges | `read_with().chunk().concurrent().gap()` |
| slow large uploads | multipart size and parallelism | `writer_with().chunk().concurrent()` |
| re-reading the same bytes | cache | `FoyerLayer` |
| cold connections / handshake cost | pool and HTTP version | `HttpClient` (the `HttpFetch` oprobe-trace provides) |
| transient errors | retry policy | `RetryLayer` |

**oprobe 6 is the tool that finds the layer stack for your workload and proves it.**
- It measures an operator.
- It traces every HTTP request underneath it. The tracer is itself a layer plus an `HttpFetch`.
- It names the cause, and each cause has exactly one remedy: a layer, or an option on a layer.
- It A/B-tests the current stack against the proposed one, judged by **your objective**.
- It prints the winning stack as Rust code and as a config value that `opendal` builds directly.

**Elegant by construction:**
- One concept (the stack).
- One artefact (the `.oprobe` file).
- One loop (measure → explain → propose a stack → prove → emit).
- The same tracing layer runs in the benchmark and in production, so the report reads the same in
  both places.

**Fun by construction:**
- Any of OpenDAL's ~70 services can be measured with the same workload:
  `oprobe run s3://… r2://… gcs://… fs:///mnt/nvme` races them side by side.
- `oprobe demo` puts a misbehaving storage service on your laptop in one second.
- The HTML report shows each request as a waterfall.
- A run file is small enough to paste into an issue.

## 3. The shape of the product

### Commands (29 → 7)

```
oprobe run   URL…  [--preset P] [--stack FILE|--set k=v] [--objective goodput|p99|cost]
oprobe fix   RUN   [--objective …] [--budget 5m]   # diagnose → candidate stacks → A/B → winning stack
oprobe diff  A B   [--gate]                         # compare runs or stacks; exit 3 on regression (CI)
oprobe show  RUN   [-o text|json|html|md]           # the report (text, JSON, a shareable HTML file)
oprobe check URL                                    # doctor: DNS/TLS/auth/clock/list, read-only
oprobe lab   [SCENARIO]                             # local S3 with faults (demo = run lab://demo)
oprobe mcp                                          # the same verbs for agents
```

- **`fix` absorbs `tune`, `verify` and today's `fix`.** A stack is only recommended after it beats
  the current one by the user's objective, by more than the noise floor.
- **`run` with several URLs absorbs `matrix`.**
- **`demo` stays as an alias.**
- **Other existing commands become flags or move into `show`:** `runs list/rm/gc` →
  `show --list`/`--rm`; `target` → URLs plus `[targets]` in the config file; `analyze` →
  `show --by stage|api|conn`; `explain` → `show --explain` and `fix`.

### Knobs = the stack

A run's spec is two parts:
- the **workload** (preset, objects, sizes, mix, duration, concurrency);
- the **`ClientStack`**: the ordered OpenDAL layers with their parameters, plus read/write options.

`--set` changes one stack value. `--stack stack.toml` sets the whole stack. Every finding's advice
and every `fix` output is a stack diff, rendered as:

```text
  stack diff (proved: goodput +31 % [+27, +35], p99 −42 %, 0 throttled; 4 A/B pairs)
  + ConcurrentLimitLayer::new(24)
  ~ RetryLayer::new().with_jitter().with_max_times(4)
  + TailCutLayer::builder().percentile(95).build()
```

The patch is emitted as Rust and as a TOML/JSON stack that `oprobe run --stack` and applications can
both read.

### Objective-first verification (fixes U1–U3)

- The user states what they care about: `goodput` (default), `p99` or `cost`. The optional
  constraint `--max-throttle 0.1%` is a constraint, not the objective.
- `fix` and `diff --gate` decide on the objective's net effect, using a sequential test with a
  learned noise floor:
  - a change that meets its narrow prediction but loses on the objective is **refuted**;
  - there is no "confirmed / traded" split.
- Every recommendation in a report states its predicted objective delta. If oprobe cannot predict
  one, the advice reads "try", not "do".
- **`run` explains and `fix` sizes.**
  - A single closed-loop run varies no load. So `run` names the cause and the layer that addresses
    it, but gives no number (fixes T1 and T2). Today it prints "c ≤ 20" with a linear prediction.
  - Numbers come only from `fix`, which sweeps the dimension the finding names and stops at the
    objective's knee. That covers limits that throttle and limits that only queue or plateau.
- Confidence is earned:
  - "high" requires the fit to explain most of the effect and to agree across repeats;
  - intervals for ratios are Wilson/beta and stay in range;
  - censored open-loop arrivals count in every percentile (T3, T8, T9).

### Front ends

- **CLI** with one-screen output: the verdict, at most three findings, the stack diff and the next
  command.
- **The app, built on nsh (owner decision D1).** `oprobe` with no arguments opens it. The same nsh
  code renders a native window (AppKit, Win32, GTK 4), or the terminal when there is no display or
  the session is over SSH. It is rebuilt as a thin view over `App` around the stack, and has no
  logic of its own:
  - **Runs**: history and targets, with live runs streaming in.
  - **Run**: the verdict and where the time went. The request waterfall of the slowest operations,
    the timeline and the heatmap.
  - **Stack**: the operator's current layer stack beside each finding's remedy layer.
    - Toggle a layer or change a value, then press *prove*. This runs `fix`'s A/B against the
      current stack and shows the objective delta with its interval as pairs come in.
    - The winning stack diff can be copied as Rust or TOML.
  - **Race**: the same workload on several services side by side (`run URL…`).
  - **Diff**: two runs or two stacks, with the gate verdict.

  It reuses the report's view model (`report/view.rs`, made complete this time), so the app, the
  terminal brief and the HTML report show the same sections from one place. Target: about 7k lines
  (16.6k today).
- **HTML report**: a self-contained file to share or attach to CI, with the waterfall, the heatmap and
  the stack diff.
- **MCP**: the same seven verbs. They map to 6 tools — `run`, `fix`, `diff`, `show`, `check`,
  `get_job` — with a total tool schema of about 8 KB or less, plus the `oprobe://runs/…` resources.

### Crates (3 → 2)

- **`oprobe-trace`** is the published library.
  - It provides `TraceLayer`, the instrumented `HttpFetch` and `Recorder`/`Snapshot`, and writes a
    snapshot as an `.oprobe` file.
  - Its dependencies are slim: no schemars, no aws-lc, no CLI error codes, and it is
    `#[non_exhaustive]` throughout.
  - It has a real overhead benchmark in CI, with a budget of ≤ 2 µs per op.
  - **Production snapshots open in the same report:**
    `handle.snapshot().save("prod.oprobe")` → `oprobe show prod.oprobe`.
- **`oprobe`** is the binary, with an internal library that is not published:
  - engine, analysis, store, lab, report, CLI, MCP;
  - the `App` layer stays as the only thing the CLI and MCP call;
  - nothing else is public API.

### What is removed

| Removed | Lines | Why, and what replaces it |
|---|---|---|
| Today's workbench views (the app is rebuilt on nsh, not removed) | ~9.6k | screens that duplicate report logic, the UI tuner that bypasses `App`, the second i18n layer; replaced by the five stack-centred views above |
| Distributed workers | 3.0k | only ever tested on localhost; one machine plus OpenDAL concurrency covers the target user |
| SDK clients (`aws-sdk`, `exec:`, 4 adapters) | 3.9k | never shipped or tested in CI; contrary to "OpenDAL-native" |
| `watch`, hand-written OTLP, HAR/CSV export | ~3.5k | oprobe-trace inside the app plus OpenDAL's `OtelMetricsLayer`/`PrometheusLayer` |
| `compat` | 0.7k | OpenDAL's own behaviour tests |
| `self-update` | 1.0k | the installer and package managers |
| `tune` as a separate engine with a Bayesian optimiser | ~2k | `fix` does a boundary search over the stack dimensions a finding names |
| Second HTTP transport ("microscope") | ~1.5k | one instrumented `HttpFetch`, which is also what production runs |
| Own cache layer (`WhiteboxCacheLayer`) | 0.5k | `FoyerLayer`, traced by the same layer |
| i18n catalog (core + UI) | ~1.2k | English output (open decision, §6) |
| Most of 67 schemas, 21 MCP tools, 77 run flags | — | about 10 schemas, 6 tools, about 20 flags |

**Target:**
- about 40–45k lines (from 104k), the app included;
- binary with the app ≤ 40 MB (from 62 MB). A CLI and MCP build without it
  (`--no-default-features --features cli`) ≤ 25 MB, for CI images and servers;
- about 400 crates in the default build (from 562), and about 250 without the app;
- the app bundles (MSI, pkg, dmg, the GTK desktop archive) stay in the release matrix;
- nsh advisories: 4 of the 5 waivers in `deny.toml` come through nsh. They are fixed upstream in nsh
  rather than waived indefinitely.

## 4. Trust: calibrate against the real world

The models are only as good as the services they were fitted to. 6.0 adds:

1. **A calibration corpus.** Short, budgeted runs (≤ US$1 each) against real S3, R2, GCS and Azure,
   and one S3-compatible store (Ceph, MinIO or OSS). The `.oprobe` files are checked in under
   `corpus/`. Every finding and every `fix` must reproduce on them in CI by replaying the analysis
   offline, with no network.
2. **The throttling model real S3 actually has:** per-prefix request-rate limits that scale up over
   minutes, and SlowDown parsed from the error body. Advice to "spread over prefixes" then becomes a
   measured stack/workload diff instead of prose.
3. **Each lab scenario is labelled with the real service behaviour it imitates.** A lab-only result
   is reported as such.

## 5. Stability after 6.0

Five majors in three days means nothing could depend on oprobe. After 6.0:
- the run file, the report JSON, the MCP tools and `oprobe-trace` are stable for the 6.x line;
- changes are additive only;
- releases are minor;
- a 7.0 needs evidence from users.

## 6. Plan and decisions

**6.0 (one release):**
1. Cut everything in §3's removal table, rebuild the nsh app around the stack, collapse the CLI to 7 commands and MCP to 6 tools, and
   merge `oprobe-core` into the binary.
2. Make the stack the central model. Every knob becomes a layer or option, every finding maps to one
   remedy, and `fix` = propose → A/B → emit, judged on the objective.
3. Wire in the layers oprobe does not use today: `ConcurrentLimitLayer`, `ThrottleLayer` and
   `FoyerLayer`.
4. Slim `oprobe-trace`: drop CLI error codes, add `#[non_exhaustive]`, add the overhead bench, save
   snapshots as `.oprobe` files.
5. Fix the 5.0 defects found by this review (v6-review.md, U and T items).
6. Build the corpus harness. The real-cloud corpus needs owner credentials (decision D3).

**Owner decisions:**
- **D1. Decided:** the visual app stays and is built on nsh (native window and terminal from one
  codebase). It is rebuilt around the stack (§3, Front ends).
- **D2.** Remove i18n (recommended for simplicity), or keep 简体中文 for the one-screen brief only.
- **D3.** Real-cloud calibration: provide budgeted credentials (S3, R2, GCS, Azure) for the corpus
  (recommended), or keep lab-only validation and label the findings accordingly.
- **D4.** Distribution: keep everything 5.0 ships, including the app bundles that follow from D1
  (recommended). Also publish a CLI-only archive for servers and CI.
