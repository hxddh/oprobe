# oprobe 6: positioning and form

**Status: proposal.** This follows the deep review of 5.0.0. The evidence is in
[v6-review.md](v6-review.md), with IDs P (product), U (walkthrough), R (architecture), T (trust) and
M (market).

**Owner direction:**
- Cut deeply.
- Don't make the product more complicated.
- Make full use of OpenDAL.
- Build something small, well made and fun to use.
- The visual app is built on nsh.

## 1. Positioning

> **oprobe is a profiler for OpenDAL operators.**
> It shows what your `Operator` really does on the wire, names the layer that fixes it, and proves
> the fix before you ship it.

**What a profiler means here:**
- A program has `perf` and flame graphs. An OpenDAL operator has oprobe.
- The unit of everything is the **`Operator`**: a service, plus a layer stack, plus read/write
  options. This is OpenDAL's own model, not one oprobe invents.

**Who it is for:** engineers who build on OpenDAL and need to know why storage is slow and what to
change. For example, the teams behind iceberg-rust, Databend, GreptimeDB, RisingWave, Vector and
sccache (M5), and anyone who uses OpenDAL from Rust or through its bindings.

**Why it is distinctive (M2, M3):**
- No other tool shows each HTTP request under an OpenDAL operation stage by stage (queue, connect,
  send, TTFB, body, backoff).
- No other tool turns that into an OpenDAL change and proves it with an interleaved A/B test.

**What oprobe is not.** Each of these is a reason to cut:

| Not | Because | Cut in 6.0 |
|---|---|---|
| a load generator for benchmarking storage servers | warp and elbencho own that, including multi-node runs (M1) | distributed workers, `matrix` |
| a monitoring system | Prometheus, APM, and OpenDAL's own metrics and otel layers already do it | `watch`, OTLP/Prometheus export |
| a CI regression gate | a different product with its own maintenance (noise floors, baselines, an Action, PR comments) | `compare` gate, baselines, GitHub Action, JUnit/Markdown |
| a cloud bill estimator | billing and Storage Lens see real traffic | cost model, price tables |
| a test harness for other SDKs | contradicts "OpenDAL-native"; never shipped or tested (R7) | `aws-sdk`, `exec:`, adapters |
| a compatibility suite | OpenDAL's behaviour tests do this | `compat` |
| an agent platform | agents run CLIs; JSON output plus a skill file is enough | the MCP server (7.5k lines, 21 tools) |

## 2. Form: one workbench, one layer, one file

```
                ┌──────────────────────────────────────────────┐
  synthetic ───▶│  oprobe  (nsh app: native window/terminal)   │──▶ proven layer diff
  workload      │  Profile → Explain → Prove                   │    (Rust / TOML)
                └──────────────────────────────────────────────┘
                              ▲            │
           production ────────┘            ▼
     oprobe-trace layer ─▶  *.oprobe file  (open, replay, compare)
```

- **One workbench: `oprobe`.**
  - It is the nsh app: a native window, or the terminal when there is no display.
  - The same verbs work without a UI as a CLI, with text or `-o json` output.
- **One layer: `oprobe-trace`.**
  - It is an OpenDAL layer plus an instrumented `HttpFetch`.
  - Add it to your own operator to profile production traffic. It writes `.oprobe` files, which the
    workbench opens like any other run.
  - It is the only published crate.
- **One file: `.oprobe`.**
  - A profile: the operator spec, the workload, every request, and the findings.
  - It replays exactly and can be pasted into an issue.

## 3. The loop: Profile → Explain → Prove

**Profile.** Get a profile in one of two ways:
- Drive a workload through an operator. Workloads are OpenDAL access patterns:
  - small objects;
  - large objects (multipart);
  - range reads (parquet-like);
  - list/stat.
- Or open a production `.oprobe` file written by `oprobe-trace`.

**Explain.** Each finding names a cause, shows the evidence (the requests themselves) and names
**one** OpenDAL remedy:

| Finding | Remedy |
|---|---|
| throttling (429/503, in-flight, rate or per-prefix limit) | `ConcurrentLimitLayer`, `RetryLayer` with jitter |
| bandwidth cap | `ThrottleLayer` |
| server stragglers | `TailCutLayer` |
| hung I/O | `TimeoutLayer` |
| small or many range reads | `read_with().chunk().concurrent().gap()` |
| slow multipart writes | `writer_with().chunk().concurrent()` |
| re-reading the same bytes | `FoyerLayer` |
| cold connections, HTTP version | the `HttpFetch` client settings |
| client CPU-bound | none in storage; reported as such |

Explain gives the cause and the remedy only. It gives no numbers, because a single run varies no load
and cannot size a change (T1, T2).

**Prove.**
- Prove compares two operators: the current one and the one with the remedy.
- It interleaves A/B runs, with a sequential test against a learned noise floor.
- It decides on **your objective**: goodput (the default), p99, or requests per second.
- Where the remedy has a size (a limit, a chunk size), Prove sweeps that one dimension and stops at
  the objective's knee.
- The result is a **proven layer diff**: the objective delta with its interval, and code to copy.

  ```text
  proved on goodput: +31 % [+27, +35], p99 −42 %, 0 throttled (4 A/B pairs)
  + ConcurrentLimitLayer::new(24)
  ~ RetryLayer::new().with_jitter().with_max_times(4)
  ```

**Fun follows from the model.**
- Comparing two operators that differ in a layer is the same operation as comparing two that
  differ in service. So `s3://…` vs `r2://…` vs `fs:///nvme` is a race with no extra feature.
- `oprobe lab` runs a misbehaving S3 on your laptop, so the whole loop works offline in seconds.

## 4. The product, concretely

**CLI: 4 commands (29 today).**
```
oprobe                     # the workbench (nsh)
oprobe run   OPERATOR…     # profile; several operators = side by side
oprobe prove RUN [--objective goodput|p99] [--with LAYER=…]   # A/B → proven layer diff
oprobe show  RUN|FILE      # the profile (text or -o json); --list for history
oprobe lab   [SCENARIO]    # local S3 with faults
```

- `OPERATOR` is a URL (`s3://bucket/prefix`), or an operator file (`op.toml`: service options plus
  layers plus read/write options), or a name defined in the config file.
- Connection problems are reported by the preflight `run` already performs, so there is no separate
  `doctor` or `probe`.

**The app: 4 views on nsh.**
- **Runs:** history, with live runs streaming in.
- **Profile:** the verdict, where the time went, the request waterfall of the slowest operations, the
  timeline and the heatmap.
- **Operator:** the current layer stack beside each finding's remedy.
  - Toggle a layer or change a value, then press *Prove*. A/B pairs stream in live.
  - Copy the winning diff.
- **Compare:** two runs or several operators side by side.

The app has no logic of its own: it calls the same service layer as the CLI, and shares one view
model with the text output.

**Kept and rebuilt:**
- `oprobe-trace` (slimmed down);
- the engine;
- the limit fitting that drives findings;
- Prove (from `verify` and `fix`; the separate tuner goes);
- the run file;
- the lab;
- the guard: budgets, run prefix, cleanup, read-only;
- the nsh app;
- text and JSON output.

**Cut entirely:**
- **Commands:** `tune` (with its Bayesian optimiser), `verify`, `fix`
  as separate commands; `compare`, baselines and the GitHub Action; `watch`, `matrix`, `compat`;
  `doctor`, `probe`; `target` management; `analyze`, `explain`; `self-update`.
- **Front ends and formats:** the MCP server; HTML, Markdown, NDJSON, CSV, HAR and OTLP outputs;
  the event stream; 60 of 67 schemas.
- **Clients and scale:** distributed workers; SDK clients and adapters.
- **Analysis side features:** the cost model; i18n (open decision D2).
- **Duplicated machinery:** the second HTTP transport; the in-house cache layer (`FoyerLayer`
  replaces it).
- **The `oprobe-core` crate as a public API:** it stays published only as an internal dependency of
  `oprobe` (§8).

**Targets:**
- about 25–30k lines (104k today);
- the binary with the app ≤ 35 MB (62 MB today) — withdrawn on 2026-11-26: size has no hard
  target and must not cost usability or function (it is still reported by CI);
- one public API: `oprobe-trace`;
- `oprobe-trace` is `#[non_exhaustive]`, has an overhead benchmark (≤ 2 µs per op) and no CLI error
  codes.

## 5. Trust

- Prove is the only source of numbers, and it judges on the objective. This fixes U1–U3, T1 and T2.
- Censored open-loop arrivals count in every percentile (T3).
- Tail attribution follows the real stage split (T4).
- "High" confidence requires the fit to explain most of the effect and to agree across repeats.
  Intervals stay in range (T8, T9).
- Throttle-driven failures are reported as throttling, not as an invalid run (T10).
- **Calibration corpus:** short, budgeted `.oprobe` profiles from real S3, R2, GCS and Azure, checked
  in. Every finding must reproduce on them offline in CI (P2, P3; decision D3).

## 6. After 6.0

- The `.oprobe` format, the JSON output and `oprobe-trace` are stable across 6.x.
- Changes are additive only, and releases are minor.
- The next major needs evidence from users (P1).

## 7. Decisions

- **D1. Decided:** the app is built on nsh.
- **D2. Decided:** the app's interface supports 简体中文 and English. It follows the system locale, and
  a setting in the app overrides it. The CLI and JSON output are English only, and only the app keeps
  a message catalog.
- **D3. Decided: there are no cloud credentials for now.**
  - Validation uses the lab, the fault proxy and the MinIO/fake-gcs/Azurite CI backends.
  - Every finding and every Prove result states the environment it was validated in. The corpus
    harness ships with lab and MinIO profiles, and real-cloud profiles can be added later without a
    format change.

## 8. 6.0 implementation contract

This section is binding for the 6.0 work.

### Workspace
- `crates/oprobe-trace`: published.
- `crates/oprobe-core`: kept as a crate for compile-time isolation. It is published only so that
  `cargo install oprobe` works. It is documented as internal, with no semver promise, and `oprobe`
  pins it with an exact `=` version.
- `crates/oprobe`: the binary.
- Features of `oprobe`:
  - `app` (the default): the nsh app (native window plus terminal);
  - `gui`: the native platforms;
  - `--no-default-features --features cli`: the CLI only, with the common cloud services
    (`--no-default-features` alone also drops the cloud services).
- Removed directories: `adapters/`, `action.yml` (and the Action docs), `crates/oprobe/src/mcp`,
  `crates/oprobe-core/src/{distributed,clients,compat,export}` except the JSON writer, and today's
  `ui/` views. `chart`, `heatmap`, `kit`, `theme` and nsh glue may be reused.

### Operator spec (`op.toml`, `oprobe.operator/6`)

```toml
url = "s3://bucket/prefix"          # any OpenDAL scheme oprobe is built with; lab:// too
[options]                            # OpenDAL service options, checked against the service
region = "eu-west-1"
[layers]                             # each key = one OpenDAL layer; absent = not in the stack
concurrent_limit = { http = 24 }                    # ConcurrentLimitLayer::with_http_concurrent_limit
retry = { max_times = 3, jitter = true, min_delay = "50ms", max_delay = "5s" }   # RetryLayer
timeout = { op = "30s", io = "10s" }                # TimeoutLayer
tail_cut = { percentile = 95 }                      # TailCutLayer
throttle = { bandwidth = "100MiB", burst = "16MiB" }  # ThrottleLayer
cache = { memory = "256MiB" }                       # FoyerLayer (in-memory)
[read]
chunk = "8MiB"
concurrent = 4
gap = "64KiB"
[write]
chunk = "8MiB"
concurrent = 4
[http]
version = "auto"          # auto | h1 | h2
keep_alive = true
```

- `OperatorSpec` replaces `TargetSpec`, `Knobs` and `ClientStack`. It builds the measured operator,
  and its *diff* renders as Rust and TOML. One value serves all three purposes.
- `--set layers.retry.max_times=5`, `--set read.gap=1MiB` and so on change one value.
- The defaults are OpenDAL's defaults, plus `retry` (OpenDAL's own recommendation) and `timeout`.

### Workload
`--preset small-files|large-objects|range-reads|list-stat`. These four replace the five presets.
Further settings: `-c/--concurrency`, `-d/--duration`, `--objects`, `--object-size`, `--rate`,
`--existing PREFIX` (read-only), `--seed`.

### CLI

| Command | Flags | stdout |
|---|---|---|
| `oprobe` | — | the app; without a display, the app in the terminal |
| `oprobe run OPERATOR… [workload] [--set k=v]… [--max-cost/requests/bytes/duration] [--read-only] [--dry-run]` | several operators run one after another on the same workload and form one comparison | the brief: verdict, at most 3 findings with their remedy, the next command |
| `oprobe prove RUN [FINDING] [--with k=v]… [--objective goodput\|p99] [--max-throttle R] [--budget DUR]` | | the proven layer diff (Rust and TOML) with its evidence |
| `oprobe show [RUN\|FILE] [--list] [--rm RUN…] [--detail] [--by stage\|api\|conn]` | | the profile |
| `oprobe lab [SCENARIO] [--bind ADDR]` | | the endpoint |

- Global flags: `-o text|json`, `-q`, `--color`, `--non-interactive`.
- `OPERATOR` = URL | `op.toml` | `[operators.NAME]` in the config file.
- `demo` is an alias of `run lab://demo`.
- Exit codes: 0 ok · 1 runtime · 2 usage · 4 budget · 5 safety · 130 interrupted.
  - 3 = Prove refuted (the change is worse on the objective).

### App service layer (`oprobe_core::app::App`)

```rust
impl App {
    fn plan(&self, req: &RunRequest) -> Result<Plan>;
    async fn run(&self, req: RunRequest, sink: EventSink, cancel: Cancel) -> Result<RunOutcome>;      // 1..n operators
    async fn prove(&self, req: ProveRequest, sink: EventSink, cancel: Cancel) -> Result<ProveOutcome>;
    fn show(&self, r: RunRef) -> Result<Profile>;  fn list(&self) -> Result<RunList>;  fn rm(&self, r: &[RunRef]) -> Result<()>;
    async fn lab(&self, req: LabRequest) -> Result<LabHandle>;
}
```

- The CLI and the app call only these.
- `EventSink` carries progress, a live summary every second, and Prove's pairs as they finish. The
  app draws from it.

### Findings → remedies
Exactly one remedy per finding. Each remedy is an `OperatorSpec` path:

| code | remedy path |
|---|---|
| `throttling` | `layers.concurrent_limit.http` (sized), plus `layers.retry.jitter` |
| `rate_limit` | `layers.concurrent_limit.http` (sized via the measured rate × latency) |
| `key_limit` | the workload's key layout. This remedy is not a layer; it is reported as advice |
| `bandwidth_cap` | `layers.throttle.bandwidth` |
| `tail_stragglers` | `layers.tail_cut` |
| `hung_requests` | `layers.timeout.io` |
| `small_ranges` | `read.gap` / `read.concurrent` |
| `slow_multipart` | `write.chunk` / `write.concurrent` |
| `repeated_reads` | `layers.cache` |
| `cold_connections` | `http.keep_alive` / `http.version` |
| `client_bound` | none (reported) |

- `run` prints the remedy path and **no number**.
- The finding catalog (`analysis/catalog.rs`) documents exactly these codes, plus `errors` and
  `invalid_run`. Every other 5.0 code is removed.

### Prove
1. **Choose the change.** It is the finding's remedy, or `--with`.
2. **Size it.** If the remedy is a size, run a bracket search over that one value with short trials
   and choose the knee of the objective, subject to `--max-throttle`.
3. **A/B test.** Interleave A B A B with a sequential test (SPRT) on the objective against a noise
   floor learned from A/A pairs. Stop when there is a decision or the budget runs out.
4. **Decide.** The verdict is `improved | worse | inconclusive` on the objective.
   - Ratio intervals are Wilson/beta.
   - Secondary metrics are shown, never decisive.
5. **Save.** Every trial run is saved as a child of the Prove run and is hidden from `show --list` by
   default.

### Run file and output
- File formats: `oprobe.run/6` (segments plus sidecars, as in 5.0) and `oprobe.report/6`.
- 5.x files are not read.
- Schemas, blessed in `schemas/` (and nothing else):
  - `report`
  - `prove`
  - `run-list`
  - `operator`
  - `error`
  - `events`
